# 팀 작업공간

이 문서에서는 장기 실행의 사용자 표시 이름으로 `team workspace`을 사용합니다.
defaultspack 프리미티브 위에 구축된 조정 표면입니다. 내부 ID,
경로 및 팩 경로는 호환성을 위해 여전히 `company`을 사용할 수 있습니다. 는
제품별 운영 회사 프로필은 다음과 같습니다.
§루미§0§; defaultspack은 일반을 소유합니다
사용하는 계약: 채팅 저장소, 에이전트 런타임, 스케줄러, 메모리, 컴팩트
컨텍스트, 도구 정책, 승인, 감사 및 작업 공간 범위 코딩.

작업 공간은 내부 팀 역할이 뒤에 있는 사용자와 대면하는 하나의 대화입니다.
그것. 클라이언트 관리자는 외부 스레드를 일관되게 유지하고 프로젝트 관리자는
코딩 엔지니어, 연구 전문가, 검토자, 운영 모니터 및
스케줄러 역할은 내부 상태와 채널을 통해 조정됩니다.

## 런타임 형태

- 팀 작업공간 프로필은 선택 사항이며 defaultspack이 아닌 팩 소유입니다.
  시작 요구 사항.
- 부트스트랩은 하나의 조직, 하나의 운영 대화 및
  논스톱 모드가 요청될 때 간격 하트비트 일정.
- 역할은 기본적으로 최소 권한입니다. 각 역할에는 필요한 도구만 제공됩니다.
  그 일을 위해.
- 모델 자체 선택은 허용 목록 기반이며 감사를 기반으로 합니다.
- 장기 실행 메모리는 결정, 사건, 핸드오프, 간결한 요약,
  무제한 성적표 증가에 대한 상태를 예약합니다.
- 역할 간 위임된 작업은 `delegation`으로 기술되어야 합니다. 이전
  `subagent` 문구는 다른 곳에 나타나는 경우 호환 언어입니다.
  별도의 아키텍처 계층이 아닌 동일한 아이디어를 중심으로 합니다.

## 보안 불변성

- 지역 정책은 권위가 있습니다. 팀 역할은 defaultspack 도구를 우회할 수 없습니다.
  정책, 승인 게이트, 경로 가드 또는 감사.
- 파일 쓰기, 파괴적인 파일 작업, 터미널 실행, git 커밋/푸시,
  외부 전송, 설정 변경 및 자격 증명에는 여전히 일반 인증이 필요합니다.
  정책에 따라 민감하다고 표시되는 경우 로컬 승인 경로.
- 원격 피어 및 외부 시스템은 정규화된 방식을 통해서만 메시지를 제출할 수 있습니다.
  입력 경로. 승인을 부여하거나, 팩을 설치하거나, 설정을 변경하거나,
  로컬 승인 토큰을 발행합니다.
- 코딩 작업은 활성 작업공간 루트에만 국한됩니다. 팀 역할이 요청할 수 있음
  코드 변경의 경우, 파일, 터미널 및 git 핸들러는 작업 공간을 적용합니다.
  경계.
- P2P는 향후 팩 또는 로컬 설정으로 활성화된 경우 메시지 수신 전용입니다. 그것
  도구 실행이나 승인 권한을 노출하지 않습니다. 참조
  §루미§0§.

## 운영 지침

지속적인 모니터링, 예약된 작업, 다중 역할을 위해 팀 작업 공간을 사용하세요.
사용자가 여전히 하나의 명확한 클라이언트 지향 스레드를 원하는 실행. 유지하다
정상 상태 묵묵부답, 증거로 사건 에스컬레이션, 내부 요약
사용자에게 권한, 자격 증명 또는 판단을 요청하기 전에 진행하세요.
