# Defaultspack ドメインコンポーネントの規則

Defaultspack は拡張機能のようなドメイン コンポーネントに移行しています。機能は次のとおりです。
`domain/<category>/<component_id>/` の下にフォルダーをドロップすることで追加できます。
マニフェストとそれが所有する小さなルール、アダプター、またはハンドラー。既存のパブリック ID、
ルート、インポート、および動作は安定したままですが、中央レジストリは
検出層と互換性層。

## フォルダーのレイアウト

正規のコンポーネント フォルダーは次の形状を使用します。

```text
domain/<category>/<component_id>/
  manifest.json
  rules.py or rules.json
  handler.py / adapter.py / inbound.py / output.py
  README.md
  tests/
```

コンポーネント ID は安定しており、小文字であり、ファイルシステムに対して安全である必要があります。パブリックID
マニフェスト内では、ドット、スラッシュ、および歴史的な名前が保持される場合があります。
はすでに API の一部になっています。

## カテゴリの名前付け

複数のドメイン指向のカテゴリを使用します。

- `webhooks`
- `integrations`
- `gateway_channels`
- `webhook_url_providers`
- `tools`
- `providers`
- `prompts`
- `templates`
- `input_profiles`
- `output_profiles`
- `audience_policies`
- `transports`
- `ui_surfaces`

カテゴリ名は、実装の詳細ではなく、所有権を説明する必要があります。のために
たとえば、LINE Webhook のデフォルトは `webhooks/line` に属しますが、LINE インバウンドは
セキュリティおよび正規化コードは `integrations/line` に属します。

## マニフェストフィールド

すべてのコンポーネント マニフェストには以下が含まれている必要があります。

- `id`: 安定したコンポーネント ID またはパブリック ID。
- `category`: フォルダー カテゴリ。
- `kind`: カテゴリ内のコンポーネントの種類。
- `version`: コンポーネントコントラクトの文字列バージョン。
- `status`: `experimental`、`stable`、または `legacy`。

推奨フィールド:

- `entrypoints`: ランタイム コードのパスまたはファイル相対エントリポイントをインポートします。
- `routes`: パブリック HTTP ルート メタデータ、メソッド、およびルート ID。
- `profiles`: コンポーネントが所有または公開する入出力プロファイル ID。
- `security`: 署名、共有秘密、承認、資格情報、またはサンドボックス ポリシー。
- `ui`: フロントエンドのグループ化、アイコン、コマンド、パネル、またはカタログのメタデータ。
- `policy`: オーディエンス、応答、ツール、またはルーティング ルール。
- `capabilities`: プロバイダー、ツール、メディア、トランスポート、およびモードの機能。
- `aliases`: このコンポーネントに解決される安定した互換性エイリアス。
- `compatibility`: 残すべきレガシーインポート、ID、デフォルト、およびシム。
- `conversion_targets`: このコンポーネントが変換またはエクスポートできる ID。
- `owner`: 所有モジュール、チーム、またはメンテナのヒント。
- `source_pack_id`: コンポーネントを提供するパック。

マニフェストはデータです。 Discovery はハンドラー コードをインポートしたり、任意のコードを実行したりしてはなりません
パイソン。ランタイムレイヤーは、コンポーネントが選択された後にのみエントリーポイントをインポートできます
使用するために。

## エントリポイント

エントリポイントは、実行時の動作を示すインポート文字列またはファイルローカル名です。

```json
{
  "entrypoints": {
    "handler": "domain.integrations.line.inbound:handle_line_webhook",
    "security": "domain.integrations.line.security:verify_signature",
    "adapter": "domain.providers.google.adapter:GoogleProvider"
  }
}
```

互換性シムは引き続き古いブロック モジュールをインポートする可能性がありますが、新しいコードはインポートする必要があります。
コンポーネント レジストリに選択したコンポーネントを問い合わせて、特定のコンポーネントをロードします。
エントリーポイントが必要です。

## ルール ファイル

ルールは、宣言型の場合は `rules.json` に存在し、宣言型の場合は `rules.py` に存在する可能性があります。
ルールには小さなヘルパー関数が必要です。ルール ファイルはコンポーネントに対してローカルに存在する必要があります
また、第 2 の中央レジストリになってはなりません。

例:

- Webhook エンドポイントのデフォルト
- 入出力プロファイル仕様
- 視聴者ポリシー
- ツールの承認/リスクのヒント
- プロバイダーモデルのデフォルト
- プロンプトレンダリングオプション
- ルートメタデータ
- UIコマンドのグループ化

## 互換性エイリアス

エイリアスには、歴史的なパブリック名が保存されます。エンドポイント ID、プロファイルが含まれる場合があります。
ID、ツール ID、プロバイダー エイリアス、モデル エイリアス、ルート名、レガシー インポート
パス。エイリアス解決は明示的かつ決定的である必要があります。

例:

- エンドポイント ID: `line-main`、`discord-main`、`slack-main`、`test-webhook`

## ルートのメタデータ

ルート メタデータは、安全な場合は常に動作を所有するコンポーネントに属します。

```json
{
  "routes": [
    {
      "id": "webhook.line.inbound",
      "path": "/webhooks/line",
      "methods": ["POST"],
      "entrypoint": "domain.integrations.line.inbound:handle_line_webhook"
    }
  ]
}
```

パブリック パスは移行中に変更してはなりません。既存のルート テーブルはそのまま残ります。
マニフェストに基づくルートが完全にカバーされ、テストされるまでフォールバックします。

## プロバイダーとモデルのメタデータ

プロバイダー コンポーネントは、プロバイダー メタデータ、認証ルール、アダプター エントリポイント、および
モデルのデフォルト。モデル カタログは、マニフェストをサポートする兄弟パックから受信することもできます。
`rumi_model_catalog_pack`など。 defaultspack はそれらと相互運用する必要があります
コピーしたり折りたたんだりするのではなく、パックします。

プロバイダー コンポーネントは、ツール レジストリまたはツール ポリシー モジュールをインポートしないでください。
プロバイダーとツールのブリッジングは、次のことを認識しているオーケストレーション層またはブローカー層に属します。
プロバイダーの機能とツールの実行の両方。

## プロンプト、プロファイル、およびポリシーのメタデータ

プロンプト コンポーネントは、独自のプロンプト ID、プロンプト テキスト/テンプレート、レンダリング ルール、および
プロンプト互換性エイリアス。入力/出力プロファイルと視聴者ポリシーは次のとおりです。
既存のレジストリ API を維持しながら、マニフェストまたはルールに基づいたコンポーネントになります。

レジストリはコンポーネント データをロードし、ユーザー定義の永続データをマージし、
互換性の検索を提供します。新しいハードコードされたデフォルトを拡張すべきではありません。

## 移行ルール

- パブリック ID、ルート、エイリアス、エンドポイント ID、プロファイル ID、ツール ID を保持します
  安定しています。
- 呼び出し元が移動するまで、古いインポートを薄いシムとして保持します。
- 古いコードを削除する前に、古いコードの隣にマニフェストに基づく検出を追加することを推奨します。
  コード。
- ランタイムを変更する前に、デフォルトをコンポーネント マニフェストまたはルール ファイルに移動します。
  行動。
- セキュリティと承認の動作を少なくとも以前と同じくらい厳格に保ちます。
- 無効なコンポーネント マニフェストでソフトが失敗し、診断が公開されます。
- ディスカバリーで複数のエコシステム パックをサポートします。

- `rumi_model_catalog_pack`をdefaultspackに折りたたまないでください。

## 中央レジストリに存在してはいけないもの

中央レジストリは、以下の主なホームであってはなりません。

- プロバイダーのエンドポイントのデフォルト
- プロバイダー固有の入出力プロファイルのデフォルト
- 視聴者ポリシーのデフォルト
- プロバイダーのホワイトリストとモデル機能のメタデータ
- ツールスキーマとリスクポリシー
- 統合固有の署名または応答ルール
- プロンプトテキストとプロンプト互換性エイリアス
- コンポーネントが所有するルートおよび UI メタデータ

中央ファイルは互換性エイリアス、サニタイズ、永続化、マージを保持する可能性があります
移行が不完全な場合のロジック、診断、およびフォールバック動作。
