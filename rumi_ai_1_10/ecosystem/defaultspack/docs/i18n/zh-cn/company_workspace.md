# 团队工作区

本文档使用`team workspace`作为长期运行的面向用户的名称
协调表面构建在 defaultspack 原语之上。内部 ID，
路由和包路径仍然可以使用`company`来实现兼容性。的
产品特定运营 公司简介位于
§鲁米§0§； defaultspack 拥有通用的
它使用的合约：聊天存储、代理运行时、调度程序、内存、紧凑
上下文、工具策略、批准、审计和工作区范围的编码。

工作空间是一种面向用户的对话，背后有内部团队角色
它。客户经理保持外部线程的连贯性，而项目经理，
编码工程师、研究专家、审稿人、运营监控员以及
调度程序角色通过内部状态和通道进行协调。

## 运行时形状

- 团队工作区配置文件是可选的并且由包拥有，而不是默认包
  启动要求。
- Bootstrap 创建或重用一个组织、一个操作对话，以及
  请求不间断模式时的间隔心跳计划。
- 默认情况下，角色具有最低权限。每个角色仅收到所需的工具
  为了它的工作。
- 模型自选基于许可名单并经过审核。
- 长时间运行的记忆更喜欢决策、事件、交接、紧凑的摘要，
  并在无限制的成绩单增长上安排状态。
- 角色之间的委派工作应描述为`delegation`。年长的
  `subagent` 措辞在其他地方出现时是兼容性语言
  围绕相同的想法而不是单独的架构层。

## 安全不变量

——地方政策具有权威性。团队角色无法绕过defaultspack工具
  政策、审批门、路线守卫或审计。
- 文件写入、破坏性文件操作、终端执行、git commit/push、
  外部发送、设置突变和凭据仍然需要正常的
  当政策将其标记为敏感时，当地的批准路径。
- 远程对等点和外部系统只能通过规范化提交消息
  输入路径。他们无法授予批准、安装包、改变设置或
  发行本地批准令牌。
- 编码工作仍然局限于活动工作空间根目录。团队角色可能会问
  用于代码更改，但文件、终端和 git 处理程序强制执行工作空间
  边界。
- P2P（如果由未来的包或本地设置启用）仅是消息入口。它
  不公开工具执行或批准权限。参见
  §鲁米§0§。

## 操作指导

使用团队工作空间进行持续监控、计划工作和多角色
用户仍然需要一个清晰的面向客户端的线程的执行。保留
正常状态沉默，用证据升级事件，并总结内部
在向用户询问权限、凭据或判断之前先取得进展。
