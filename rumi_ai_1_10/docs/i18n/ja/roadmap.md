# Rumi AI OS — ロードマップ

## 🚀 フェーズ V: Rumi Viewer + Pack デスクトップ アプリケーション [最も重要/最優先]

> **このフェーズは他のすべてのタスクよりも優先されます。**
> Rumi を「ターミナル不要のデスクトップ アプリ」として配布できるようにするための最も重要なマイルストーン。

### アーキテクチャの概要

**インストーラー（ユーザーに配布）の内容：**

1. **Rumi コンソール** (rumi ランチャー、Rust) - トレイに常駐します。カーネルプロセス管理。通常、ユーザーはこれに気づきません。
2. **Rumi Viewer** (Tauri) — Pack フロントエンドを表示する汎用 WebView アプリ。ユーザーが日常的に使用するメインアプリ。
3. **bundled/uv** — Python 環境を構築します。
4. **app/** (rumi_ai_1_10/) — カーネル ソース コード。**Rumi Viewer とは:**
・Tauriで作成した汎用WebViewアプリケーション
- `web_mount`のPackで宣言されたフロントエンド(HTML/CSS/JS)を表示します。
- カーネル API (localhost:8765) にのみ接続できます。外部サイトに行けない
- Pack はフロントエンド ファイルを渡すだけです。ホスト環境（サンドボックスWebView）には触れないでください。
- パック バックエンドは Docker コンテナ内で分離して実行されます
- 「フロントエンド = サンドボックス WebView」+「バックエンド = Docker 分離」による二重分離

**セキュリティモデル:**
- ビューアに何かを表示するには、`viewer:display` 機能が必要です (機能ベースの権限管理)
- ビューアは権限があればどのパックでも使用できます
- `core_viewer_capability`は、`core_docker_capability`および`core_communication_capability`と同じ位置にあります。
- パックが独自のデスクトップ アプリ (Tauri/Electron など) を提供することは可能ですが、これは「危険な権限」 (`desktop_app.execute`) として扱われ、明示的なユーザーの承認が必要になります。
- ほとんどのパックは安全な Viewer ルートを使用する必要があります。

**ユーザーエクスペリエンス:**
1. ユーザーがインストーラー (.dmg/.exe) を使用してインストールします。
2.「Rumi Viewer」をダブルクリックします。
3. Rumi Console が自動的に起動 → カーネルがバックグラウンドで起動
4. ビューアにコントロールパネルが表示される
5. パックをインストール → AIチャットなどのパックのフロントエンドがビューアに表示されます。
6. 端末には絶対に触れないでください

**起動フロー:**
```
Rumi Viewer 起動
  → Kernel ヘルスチェック（localhost:8765/health）
  → 未起動なら Rumi Console を自動起動
  → Kernel ready を待機
  → Viewer が localhost:8765/panel/ を WebView に表示
  → ユーザーが Pack を選択 → Pack のフロントエンドに遷移
```

**競合/エラーの処理:**
- 競合と起動エラーは、Rumi Console (トレイ アイコン) を使用して表示および対処できます。
- ビューアは表示専用です

## 0. 北極星 (ビジョン)

- **インフラストラクチャを必要としない基盤**: 正式版にはドメイン概念 (チャット/ツール/プロンプト/UI など) がなく、「実行、承認、分離、監査、権限」などの OS のようなメカニズムのみが提供されます。
- エコシステムはサードパーティによって作成されたものと想定され (悪意のある想定)、コアは **承認が必要**、**Docker 分離 (厳密に推奨)**、**フェイルソフト**、**監査ログ** です。

---

## 1. 設計原則

### 1.1 えこひいきをしない

公式コアは、「API キー」、「ツール」、「チャット」などの意味を解釈しません。 公式に提供される汎用メカニズム: フロー実行、認可ゲート (ハッシュ検証)、分離実行 (Docker/UDS)、Trust + Grant (機能)、監査ログ。

### 1.2 悪意の前提 (脅威モデル)

パック 作成者に悪意がある可能性を常に想定してください。 Packの実行は基本的にDocker`--network=none`です。外部通信とホスト権限は機能 (Trust + Grant) に割り当てられます。

### 1.3 フェイルソフト

一部が壊れてもOS全体が止まることはありません。視覚化して診断と監査を続行します。

### 1.4 ホスト権限の単一エントリ ポイント

ホスト上の危険なこと（外部通信、ファイルアクセス、アプリケーション、端末の更新など）はPackが直接行うのではなく、機能を介して行われるため、勝手に行うことはできません。

---

## 2. 概念の整理

### 2.1 パック/プリンシパル/機能

- **プリンシパル**: 権限決定の対象。 v1 は、操作を簡素化するために、pack_id 単位に基づいています。
- 機能は `permission_id` で要求され、Trust (sha256) および Grant (プリンシパル × 許可) で付与されます。

### 2.2 パックインパック (レイヤリング)

`parent__child`と同様に階層はpack_idで表現され、上位が下位を制限する(上位が許可しない限り下位は移動しない)。

目的: バンドル配布、運用の統合管理、親子権限制約。

> 注: ディレクトリ階層≠ セキュリティ境界。強制力は「ホスト側ゲート（能力・実行装置）」によって確保されます。

### 2.3 店舗/ユニット (共用エリアと再利用ユニット)

ユーザーやエコシステムが任意に作成できる共有領域（Store）と、その領域内で再利用可能なユニット（Unit）は、汎用プラットフォームとして価値があります。ユニットは `data / python / binary` などにすることができます。実行ユニットはパック承認 + ユニット トラスト (sha256 ホワイトリスト) に基づいています。

実行モードは、特権に応じて選択できます (修正されません): パック コンテナー、ホスト機能、専用サンドボックス (将来)。

## 3. 公式コア財団のリスト

### 3.1 依存関係 (pip) の概要

パックには`requirements.lock`が含まれます。 Wheel-only がデフォルトです (sdist は例外として承認されています)。ビルダーコンテナで、ダウンロード→インストールを行います（インストールはオフラインです）。実行時に、RO マウント + PYTHONPATH を使用してサイト パッケージを表示します (コンテナーは network=none を維持します)。

### 3.2 ケイパビリティハンドラ候補の紹介（承認ワークフロー）

候補者はエコシステムに含まれます。スキャン→保留中→承認/拒否→ブロック（3回拒否）。承認 信頼登録 + コピー + レジストリのリロード。クールダウン 1 時間、ブロックされた場合はブロックが解除されるまで通知されません。

### 3.3 シークレット (API キーの保存)

`.env`を避けてください（事故率を減らします）。 `user_data/secrets/`に格納し、ログに値を出力しません。秘密ファイルをパックに見せないでください。取得は基本的に能力によって行われます (例: `secrets.get`)。

### 3.4パックの配布形式

入力 3 形式: フォルダー / `.zip` / `.rumipack` (zip 互換)。推奨：根元に1パック。将来的にはマルチパック アーカイブ (パック イン パック) に拡張できます。

### 3.5 アプリケーションのアップデート(自動アップデート禁止)

正式版は自動更新されません。取得→ステージング→分離を適用します。 applyは危険なのでcapability(`pack.update`)に移動したいと思います(v1は運用APIとしても使えます)。まず、単一の Pack_id を適用します。

### 3.6 実行 (Python/バイナリ)

Pack の通常の実行は Docker 分離で確立されるため、ホストに Python がインストールされていない場合でも (Docker があれば) 問題ありません。ホスト上で動作するもの（ケイパビリティハンドラなど）については、将来的にはRumi自体を単一の実行ファイルにするか（Pythonも含む）、ハンドラをOSごとのバイナリにするか（両方可能）が必要になります。

### 6.5 語彙を使用したコンポーネント出力キーの正規化 (パック互換性レイヤー)

- 🧩 コンポーネントタイプごとの出力キーの自動正規化
- 🧩 vocab_registry の同義語グループ + コンバーターをフロー実行パスに統合
- 🧩正規化タイミングの標準化（ctx格納前と参照時）
- 🧩 パック側で vocab.txt を使用した同義語宣言の推奨パターンの開発

#### 背景

サードパーティのパック開発中に発見された問題。 kernel_coreの_execute_handler_step_asyncは、フローステップの戻り値をそのままctx[step["output"]]に格納します。つまり、デフォルトのパックが {"content": "...", "model_name": "..."} を返す構造で、フローが ${ctx.ai_response.content} を参照している場合、別のパックのように {"text": "...", "model_name": "..."} を返すパックに置き換えた瞬間に、すべてのフロー ステップでコンテンツが null になり、中断されてしまいます。

vocab_registry にはこの問題を解決するメカニズムがすでに備わっていますが、「フロー実行パスでの自動適用」が欠けています。

#### 提案された実施計画

**方法 A (保存中の正規化 - 推奨)**: ctx を kernel_core に保存する前に、vocab_registry 内の優先用語に変換します。数行を変更するだけで、既存のメカニズムを利用できます。**方法 B (参照の正規化)**: _resolve_value を使用したシノニム フォールバック。保存されたデータは変更されませんが、解決パスは複雑になります。**方法 C (オプトイン正規化)**: フロー ステップで正規化: true フラグを設定するか、コンポーネント マニフェストで Output_vocab_group を宣言します。既存の製品には影響ありませんが、パック作成者はこの点に注意する必要があります。
